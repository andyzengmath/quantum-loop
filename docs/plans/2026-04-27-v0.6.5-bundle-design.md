## Per-story design notes

### US-001 — G26: `do_audit` summary split

**Problem:** `do_audit` increments `ok_count` for ANY non-`FAIL` row. Pre-v0.6.4 every metric was binary OK-or-FAIL, so "X/Y metrics on target" was accurate. v0.6.4's `_audit_pre_impl_review_coverage` (US-005 of v0.6.4) introduced WARN states. Now WARN rows are silently counted as on-target. `tests/test_audit.sh` Test 33 asserts the misleading wording.

**Decision:** Split the summary into three counts. Replace the existing summary line with:

```
Summary: 6/7 OK, 1 WARN, 0 FAIL.
```

When all rows are OK (no WARN, no FAIL), keep the trailing-period clean. When any FAIL exists, the audit still exits non-zero (existing behavior preserved). WARN does NOT trip exit code (existing behavior preserved).

Implementation: in `do_audit`, walk `ROWS[]` once and accumulate three counters by parsing the `|FAIL|`, `|WARN|`, `|OK|` substrings. Print `"Summary: <ok>/<total> OK, <warn> WARN, <fail> FAIL.\n"`.

**Files:** `quantum-loop.sh` (`do_audit` summary), `tests/test_audit.sh` (Test 33 expectation flips from "7/7 metrics on target" to "6/7 OK, 1 WARN, 0 FAIL"; new assertions for the all-OK case + multi-WARN case).

**Verification:** Test 33 + 2 new assertions: synthesize a 3-row fixture with 3 OK → "Summary: 3/3 OK, 0 WARN, 0 FAIL.". Synthesize a 3-row fixture with 1 OK + 2 WARN → "Summary: 1/3 OK, 2 WARN, 0 FAIL.". Synthesize a 3-row fixture with 1 OK + 1 WARN + 1 FAIL → exit code 1 + "Summary: 1/3 OK, 1 WARN, 1 FAIL.".

### US-003 — G25: conflict-auditor sort enumeration

**Problem:** `agents/conflict-auditor.md` Step 4 sort instruction reads "Sort the `fileConflicts` array by severity (high first, then medium, then low)." Rule 0 (PR #60) added `none`; Rule 0.5 (v0.6.4 / US-006) added `warning`. Neither addition updated the sort prose. Agents following the instruction literally have indeterminate ordering for `none` and `warning` entries.

**Decision:** Update the sort instruction to enumerate all 5 severities in order:

```
high → medium → low → warning → none
```

Rationale for the order: `high` is most-impactful. `warning` is informational (above `none` because it's a real signal — count>1 CHANGELOG case — but below `low` because it doesn't block). `none` is "no conflict" / informational only.

**Files:** `agents/conflict-auditor.md` (Step 4 sort prose), `tests/test_changelog_ownership.sh` (extend with a sort-order assertion: synthesize a fixture with all 5 severities and verify the documented order is enforceable via grep on the spec text).

**Verification:** new assertion in `tests/test_changelog_ownership.sh`: `agents/conflict-auditor.md` contains the substring `"high → medium → low → warning → none"` (or the equivalent literal enumeration). Plus a structural assertion that all 5 severity strings appear in the doc.

### US-004 — G28: `references/risk-mitigation-language.md` checklist

**Problem:** The v0.6.4 design doc said "Use flock-style atomic append... Document as US-002 test fixture." This was insufficient guidance: the implementer added flock around the row append but left the header bootstrap outside the lock. `/soliton:pr-review` caught this at conf 90; fixed inline in `c89ba13`. The general lesson: risk-mitigation prose in design docs should enumerate the operations that need to be inside the critical section, not just name the technique.

**Decision:** Ship `references/risk-mitigation-language.md` with:

1. **Section: "Risk-mitigation prose: enumerate operations, not just techniques"** — the rule + the v0.6.4 cautionary tale.
2. **Section: "Concurrency checklist for design docs"** — when proposing a "use flock", "use mutex", "use semaphore", "use atomic-rename", etc. mitigation, the design doc MUST enumerate:
   - The shared mutable state (file, var, queue, etc.)
   - The full set of observably-coupled operations (read + check + write, not just write; bootstrap + append; check-then-act atomicity)
   - The race window WITHOUT the mitigation (concrete interleaving example)
   - The race window WITH the mitigation (concrete interleaving example showing the mitigation works)
3. **Section: "Other risk-mitigation language patterns"** — short-form rules:
   - "Validate input X" → enumerate which fields, which validation rules, which failure mode
   - "Handle malformed Y" → enumerate which malformed forms, what the function returns/raises
   - "Atomic update Z" → enumerate atomicity scope (single-write vs multi-write transaction)

**Files:** `references/risk-mitigation-language.md` (NEW), `tests/test_risk_mitigation_language.sh` (NEW). Optional cross-link insert in `references/finding-severity.md` (1 line) since both docs guide design-doc + review craft.

**Verification:** new test: structural assertions that the doc has 3 sections (risk-mitigation rule + concurrency checklist + short-form rules), the concurrency checklist has the 4 enumerated requirements, plus a substring assertion for the v0.6.4 cautionary-tale citation. ~8 assertions.

### US-005 — G18: `--audit` WARN drill copy improvement

**Problem:** `_audit_pre_impl_review_coverage` emits `pre-impl-review-coverage|0/3 stages|yellow|WARN|no metrics CSV` (or "no recent runs" / "missing some stages"). Operators on a fresh checkout see this and reasonably assume "the audit is broken." It's not — the metric correctly reports that no v0.6.4-instrumented planning has run yet. The drill text should clarify this expectation.

**Decision:** Update the `missing-csv` WARN message specifically (the most-common state on a fresh install): from `"no metrics CSV"` to `"no metrics CSV (expected on first run after v0.6.4 install — invoke /ql-brainstorm/spec/plan to populate)"`. Other WARN states (`no recent runs`, `missing some stages`) keep their existing concise messages — they're informative as-is.

**Files:** `quantum-loop.sh` (`_audit_pre_impl_review_coverage` `missing-csv` branch), `tests/test_audit.sh` (extend Test 28 expectation to match the new drill text).

**Verification:** existing Test 28 (missing-csv WARN state) updated; new assertion: the drill text contains the substring `"(expected on first run"`. Other 3 WARN-state assertions remain unchanged.

### US-006 — G20: README "Self-modifying execution" section

**Problem:** Every release's PIPELINE_REPORT_vX has explained "the orchestrator ran on master HEAD; the new wires apply to NEXT runs." Operators may be surprised on first encounter. A permanent README section closes this expectation gap.

**Decision:** Add a `## Self-modifying execution` section to the project README near the existing pipeline-overview prose. One paragraph:

> Quantum-loop is self-modifying: each release ships a bundle that often modifies the orchestrator, agent prompts, and skill prompts that the orchestrator ITSELF uses. The orchestrator running a given release executes on the PREVIOUS release's semantics — so the new wires apply to runs starting AFTER the bundle merges, not to the bundle's own dogfood execution. This is by design: an orchestrator cannot safely apply a diff to itself in flight. Operators should expect first-run signals (`metrics/`, audit-trail captures, severity-rubric calibration) from each release to land on the FIRST run of the SUBSEQUENT release.

Plus a short example: "v0.6.4 added pre-impl-review persistence; the v0.6.4 dogfood ran on v0.6.3 master HEAD, so its CSV is empty by design. v0.6.5's first run is the first to populate the CSV."

**Files:** `README.md` (new section), `tests/test_readme.sh` (NEW or extend if exists; assertion: README contains the section heading + key phrase "self-modifying" + at least one example release).

**Verification:** new test: structural assertion that README has `## Self-modifying execution` heading; substring assertions for "self-modifying", "previous release's semantics", "v0.6.4" example.
