# Design: v0.7.0 — pre-impl-review maturation (G12-G17)

**Date:** 2026-04-26
**Status:** Approved (user-confirmed Option α from `idea-stage/IDEA_REPORT_v4.md`)
**Source:** `idea-stage/IDEA_REPORT_v4.md` §G12 / G13 / G14 / G15 / G16 / G17 (six gaps surfaced by v0.6.3 dogfood)
**Approach:** 7 stories — 6 G-track maturations of the v0.6.3 advisory pre-impl-review trilogy (P5.B4-design / -PRD / -plan) + 1 retrospective
**Target version:** 0.7.0 (minor bump from 0.6.3; opens the "review-system maturation" arc, all mechanisms additive + opt-in)
**Target effort:** ~3-5 days (single-developer; ~2-3 days with parallel waves)

## Overview

v0.6.3 shipped three advisory pre-impl-review stages (design / PRD / plan exits) but the v0.6.3 dogfood retrospective surfaced six gaps: the FINDING_START..FINDING_END output protocol has no parser, no persistence, no severity rubric, no audit-coverage metric, and the sprint-contract test-pattern regex is duplicated in 4 places. v0.7.0 closes all six.

The bundle is **instrumentation, not expansion**. We're not adding new reviewer mechanisms — we're making the three existing reviewers measurable, calibratable, and DRY enough that v0.7.x can promote any of them from advisory to blocking with confidence-from-data rather than confidence-from-feel.

Per the v4 report's recommendation: "highest leverage v0.7 candidates: G13 → G14 → G12 → G16, with G17 as stretch." The bundle adds G15 as well (a 5-line doc edit) because its scope cost is negligible and it eliminates a real future-planner collision risk on CHANGELOG.md.

The 7-story bundle is **minor-tier** but stays additive:
- No breaking changes to existing skills, agents, or libraries
- All new mechanisms are opt-in (env vars / new flags) or non-blocking (advisory findings remain advisory)
- Schema additions are backward-compatible
- No new external dependencies

**Out of scope for v0.7.0** (queued for v0.7.1+):
- P5.B2 (bidirectional reviewer) — needs G13's persistence baseline first
- P5.B3 (`/ultrareview` parallel pattern) — composes on B2
- P5.B5 (AgentGA tournament) — cost-quality tradeoff needs P5.C1 baseline
- Promotion of any pre-impl-review stage from advisory → blocking — explicitly deferred until ≥1 release of G13 baseline data has accumulated
- P5.C frontier (HiveMind, GEPA, Skilldex) — all deferred

## Per-story design notes

### US-001 — G12: `lib/finding-synth.sh`

**Problem:** `agents/spec-reviewer.md` documents the `FINDING_START..FINDING_END` output protocol for design-review / prd-review / plan-review modes, but no parser exists. Operators see a stream of text on stderr and have no way to count, categorize, or persist findings.

**Decision:** Ship `lib/finding-synth.sh` with three pure functions (no side effects, no external state):

- `parse_findings(stage_name, stream)` — reads stdin (the reviewer's stderr capture), emits JSON array `[{category, severity, file, line, evidence, suggestion}, ...]`. Skips malformed blocks with a single stderr warning.
- `summarize_findings(stage_name, findings_json)` — emits `{stage, count, by_severity: {critical, high, medium, low}, by_category: {...}}` JSON object.
- `format_summary_line(summary_json)` — emits the existing `[REVIEW] <stage>-review complete: <N> findings (<crit>/<high>/<med>/<low>)` text the modes already log, but derived from the parsed structure rather than the agent emitting it manually.

**No skill changes in this story.** Pure library. US-002 wires it.

**Files:** `lib/finding-synth.sh` (NEW), `tests/test_finding_synth.sh` (NEW).

**Verification:** synthetic stderr fixture with 4 findings (1 critical, 1 high, 2 medium, mixed categories) → parser emits 4 entries; summarize returns matching counts; format_summary_line emits the expected text. Malformed block test: incomplete `FINDING_START` (no `FINDING_END`) → parser emits warning to stderr and continues with the well-formed remainder.

### US-002 — G13: persist parsed findings + aggregate

**Problem:** Even with US-001's parser, findings still vanish at end-of-skill. v0.6.3's `[REVIEW] design-review complete: 2 findings (0/0/1/1)` line is real but ephemeral. We promised "baseline data accumulates" — that requires persistence.

**Decision:** Two-layer persistence.

1. **Per-run snapshot** at `.handoffs/<stage>-review-findings.json` (one of `design`, `prd`, `plan`). Schema:
   ```json
   {
     "stage": "design",
     "timestamp": "2026-04-26T10:00:00Z",
     "designPath": "docs/plans/2026-04-26-v0.7.0-bundle-design.md",
     "summary": { "count": 2, "by_severity": {...}, "by_category": {...} },
     "findings": [...]   // raw parsed array from US-001
   }
   ```
   Overwritten on each run of the same stage; gitignored (operators may want to inspect without committing).

2. **Aggregate ledger** at `metrics/pre-impl-review-findings.csv` (committable). One row per stage-run with columns `timestamp,stage,prd_or_design_path,count,critical,high,medium,low`. Append-only; rotated daily if it ever exceeds 10K rows (deferred — current usage is ≤3 rows per release).

   File **not** gitignored — these CSV rows ARE the baseline data. Each row reproduces what `--audit` (US-005) will surface.

**Wiring:** add a single shell snippet to each of the 3 SKILL.md post-review blocks. Pseudocode:
```bash
REVIEW_LOG=$(mktemp)
MODE=design-review DESIGN_PATH="$DESIGN_PATH" \
  claude --headless "..." 2>"$REVIEW_LOG" || true

source "$REPO_ROOT/lib/finding-synth.sh"
source "$REPO_ROOT/lib/finding-persist.sh"
findings=$(parse_findings design < "$REVIEW_LOG")
summary=$(summarize_findings design "$findings")
persist_review_findings design "$DESIGN_PATH" "$summary" "$findings"
```

**Files:** `lib/finding-persist.sh` (NEW), `skills/ql-brainstorm/SKILL.md` (Phase 4d block extended), `skills/ql-spec/SKILL.md` (post-PRD-review block extended), `skills/ql-plan/SKILL.md` (Step 9 block extended), `tests/test_finding_persist.sh` (NEW), `.gitignore` (add `.handoffs/*-review-findings.json`).

**Verification:** new test feeds three synthetic stages through the persistence pipeline; asserts (a) `.handoffs/<stage>-review-findings.json` exists with valid schema, (b) `metrics/pre-impl-review-findings.csv` has 3 appended rows, (c) re-running the same stage overwrites the snapshot but appends a NEW row to the CSV (idempotency for snapshot, append for ledger).

### US-003 — G14: extract `SPRINT_CONTRACT_TEST_REGEX` constant

**Problem:** The regex `(test_|\.test\.|spec|pytest|^bash tests/|^npm test)` is duplicated verbatim in 4 places: `agents/orchestrator.md` Step 2.5 (lines 287-288), `skills/ql-plan/SKILL.md` Step 8 (lines 710-711), `tests/test_sprint_contract.sh` Test 6 (lines 166, 196, 226), `tests/test_sprint_contract_ql_plan.sh`. A single regex change requires touching all 4 — a 4-way drift surface that's already bitten dogfood once.

**Decision:** Extract into `lib/handoff.sh` as a documented constant at top of file (right after the stage-order constant):

```bash
# Pattern matching test-pattern commands for Sprint-Contract expectedTests.
# Used by orchestrator.md Step 2.5 + ql-plan SKILL.md Step 8 + sprint-contract tests.
# Update via this single source of truth — historical inline copies are violations.
if [[ -z "${SPRINT_CONTRACT_TEST_REGEX+x}" ]]; then
readonly SPRINT_CONTRACT_TEST_REGEX='(test_|\.test\.|spec|pytest|^bash tests/|^npm test)'
fi
```

Both call sites in markdown (`orchestrator.md`, `ql-plan/SKILL.md`) become:
```bash
source "$REPO_ROOT/lib/handoff.sh"
# ... uses $SPRINT_CONTRACT_TEST_REGEX inside jq via --arg ...
```

The jq `test()` call goes from `test("(test_|\\.test\\.|...)")` to `test($pattern)` with a `--arg pattern "$SPRINT_CONTRACT_TEST_REGEX"` injection. Tests update the same way.

`references/sprint-contract.md` updates the `expectedTests` row's bracketed reference from the inline regex to "see `lib/handoff.sh::SPRINT_CONTRACT_TEST_REGEX`".

**Files:** `lib/handoff.sh` (add constant), `agents/orchestrator.md` (Step 2.5 jq update), `skills/ql-plan/SKILL.md` (Step 8 jq update), `tests/test_sprint_contract.sh` (Test 6 inline-regex blocks updated), `tests/test_sprint_contract_ql_plan.sh` (same), `references/sprint-contract.md` (one-line doc update).

**Verification:** existing 16 sprint-contract assertions remain green. New assertion: `grep -c 'test_|\.test\.|spec|pytest' agents/orchestrator.md skills/ql-plan/SKILL.md` returns 0 (no inline duplicates remain — only the imported constant). Add positive: `grep -q 'SPRINT_CONTRACT_TEST_REGEX' lib/handoff.sh agents/orchestrator.md skills/ql-plan/SKILL.md` succeeds in all 3 files.

### US-004 — G16: `references/finding-severity.md` + cross-link

**Problem:** The 3 advisory pre-impl-review modes emit findings with `severity: critical|high|medium|low` but there's no rubric. Without calibration, "critical" findings on design-review will compete with "critical" findings from quality-reviewer post-impl. When G13's persistence + G17's audit metric come online, ungrounded severity will produce noisy data.

**Decision:** Ship `references/finding-severity.md` with three sections — one per mode (`design-review`, `prd-review`, `plan-review`) — each containing 4 severity rows with a short rubric + 1 example each.

Rubric template (per mode, per severity):

| Severity | Rubric | Example |
|---|---|---|
| critical | Findings that would cause the next pipeline stage to fail or produce malformed output. | (mode-specific) |
| high | Findings that would propagate ambiguity and cause re-work in a later stage. | (mode-specific) |
| medium | Stylistic / completeness gaps — fixable but won't cause regressions. | (mode-specific) |
| low | Polish / convention drift. | (mode-specific) |

Then cross-link: each of the 3 mode sections in `agents/spec-reviewer.md` adds one line above its Output format block: `> See [references/finding-severity.md](../references/finding-severity.md#<mode>) for severity calibration.`

**Files:** `references/finding-severity.md` (NEW), `agents/spec-reviewer.md` (3 cross-link insertions, one per mode section), `tests/test_finding_severity.sh` (NEW).

**Verification:** new test asserts (a) `references/finding-severity.md` has 3 mode sections (`## design-review`, `## prd-review`, `## plan-review`); each has all 4 severity rows; (b) each mode section in `agents/spec-reviewer.md` has a cross-link to `references/finding-severity.md`.

### US-005 — G17: `--audit` pre-impl-review-coverage metric

**Problem:** `quantum-loop.sh --audit` reports 6 metrics (branches/orphan-worktrees/conflicts/cpc-files/test-suites). v0.6.3 added 3 advisory review stages but they don't surface in --audit. Operators have no visibility into whether their pipeline is actually running the advisory checks.

**Decision:** Add a 7th metric row `pre-impl-review-coverage` to `do_audit`. Reads `metrics/pre-impl-review-findings.csv` (written by US-002), counts unique stage values in the most recent 7 days, emits `<stages_run>/<stages_possible>` (denominator is always 3: design + prd + plan).

```bash
_audit_pre_impl_review_coverage() {
  local csv="metrics/pre-impl-review-findings.csv"
  if [[ ! -f "$csv" ]]; then
    printf 'pre-impl-review-coverage|0/3 stages|yellow|WARN|no metrics CSV (pre-impl reviews never ran)\n'
    return
  fi
  local since
  since=$(date -u -d '7 days ago' +%FT%TZ 2>/dev/null || date -u -v-7d +%FT%TZ 2>/dev/null || echo "1970-01-01T00:00:00Z")
  local stages
  stages=$(awk -F, -v since="$since" 'NR>1 && $1>=since {print $2}' "$csv" | sort -u | wc -l | tr -d ' ')
  if (( stages == 3 )); then
    printf 'pre-impl-review-coverage|3/3 stages|green|OK|\n'
  elif (( stages > 0 )); then
    printf 'pre-impl-review-coverage|%d/3 stages|yellow|WARN|missing some stages\n' "$stages"
  else
    printf 'pre-impl-review-coverage|0/3 stages|yellow|WARN|no recent runs (last 7 days)\n'
  fi
}
```

Wire into `do_audit`'s `ROWS+=(...)` array.

**Files:** `quantum-loop.sh` (new helper + new ROWS entry), `quantum-loop.ps1` (parity — emit the same row from the PS1 audit shim if one exists; if not, OK to skip per current divergence pattern), `tests/test_audit.sh` (extend to assert the new row appears with all three states: missing-csv → WARN, partial → WARN, complete → OK).

**Verification:** existing audit assertions remain green; new assertions exercise the 3 states with synthetic CSV fixtures.

## Architecture / cross-cutting concerns

**Two new lib modules.** `lib/finding-synth.sh` (US-001, parser) and `lib/finding-persist.sh` (US-002, persistence) follow the existing `lib/` conventions: bash 4.3+, source-friendly (no shell flags at source time, strict mode only in CLI-entry block at file bottom), idempotent. Both are pure additions — no existing module needs to import them at v0.7.0; only the 3 SKILLs do.

**Library invocation pattern.** Both new lib modules support both `source` (function-call style) AND `bash lib/finding-synth.sh <subcmd>` (CLI style), matching `lib/handoff.sh`'s pattern. The SKILLs use the `source`-and-call pattern for performance (no subprocess fork per finding).

**Persistence vs gitignore policy.**
- Per-run snapshots at `.handoffs/<stage>-review-findings.json` are **gitignored** (operators inspect locally; no value in committing).
- Aggregate ledger `metrics/pre-impl-review-findings.csv` is **NOT gitignored** — these rows ARE the baseline data future calibration depends on. New `metrics/` directory created with one file. `.gitignore` left untouched for `metrics/`.

**No schema breakage.** Sprint-Contract schema (US-003 G14) is pure refactor — same regex behavior, single source of truth. Existing sprint-contract files load identically.

**Failure semantics for new stages.**
- US-001 parser tolerates malformed FINDING blocks (warns + continues).
- US-002 persistence tolerates missing dir (creates), missing log (skips with warning).
- US-005 audit metric tolerates missing CSV (reports `0/3 stages, WARN`).

All three preserve "advisory does not block pipeline" — no v0.7.0 mechanism can abort a `/ql-brainstorm`, `/ql-spec`, or `/ql-plan` invocation.

**Self-modifying-orchestrator caveat.** Per v0.6.3 PIPELINE_REPORT, when this bundle modifies `agents/orchestrator.md` (US-003 Step 2.5) and the 3 SKILL.md files (US-002), those changes apply to the NEXT run, not the current dogfood. The current dogfood's pre-impl-review findings will NOT be persisted because the orchestrator runs on master HEAD = v0.6.3. Document this explicitly in PIPELINE_REPORT_v5; the v0.7.1 dogfood will be the first to populate `metrics/pre-impl-review-findings.csv` end-to-end.

## Risk + mitigations

| Risk | Likelihood | Mitigation |
|---|:-:|---|
| US-001 parser silently drops a malformed block, hiding a critical finding | LOW | Test fixture covers malformed input; warning emits to stderr per dropped block. |
| US-002 CSV append race when 2 SKILLs run concurrently | LOW | Use `flock`-style atomic append via `lib/json-atomic.sh::write_quantum_json` pattern (a small shim that wraps `flock -x` around the append). Document as US-002 test fixture. |
| US-003 sourcing `lib/handoff.sh` from a markdown-fenced bash block confuses agents that misinterpret `source` as setup | LOW | The pattern is already used in v0.6.3 (`source "$REPO_ROOT/lib/json-atomic.sh"` in orchestrator.md Step 8). No new convention. |
| US-004 severity rubric examples become outdated as modes evolve | MED | Tests check structural integrity (4 rows × 3 modes), not example wording. Refresh examples each release as part of retrospective. |
| US-005 `metrics/` directory becomes the wrong-answer-cache if a v0.7.x bug populates incorrect counts | LOW | CSV is append-only; older rows are recoverable via `git log -- metrics/pre-impl-review-findings.csv`. Worst case: truncate and start fresh. |
| US-006 conflict-auditor severity-classification logic isn't centralized — may live in 2 places | LOW | First-task discovery: confirm where it lives (`agents/conflict-auditor.md` vs a `references/` doc). Update only the actual location. |
| Wave-1 file-conflict on `skills/ql-plan/SKILL.md` (US-002 + US-003 both touch) | MITIGATED | dependsOn chain serializes US-003 → US-002. dag-validator's Rule 0 will classify as `none` severity (different sections). |
| `metrics/pre-impl-review-findings.csv` accumulates noise from operators experimenting locally | MED | Document in `references/finding-severity.md` that the CSV is a project-wide baseline; operators can ignore via `QL_SKIP_PRE_IMPL_REVIEW=design,prd,plan` (already exists from v0.6.3). |
