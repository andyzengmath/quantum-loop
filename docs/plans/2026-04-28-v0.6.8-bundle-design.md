## Per-story design notes

### US-001 — N6: orchestrator stale-detection heuristic

**Problem:** v0.6.7's orchestrator subagent abandoned the cycle after US-001 — set status to `in_progress`, made the test_audit.sh edit, then drifted into self-narration about "later stories". 1 story shipped of 7 expected. Parent agent had to detect drift via git log + status check and take over manually.

**Decision:** Add a "Self-monitoring guard" subsection to `agents/orchestrator.md`'s instructions. Concrete rules:

1. **Before any non-current-story reasoning**, check: is the current `in_progress` story's commit landed? If no → reset to that story's task list.
2. **Forbidden idioms** (regex-recognizable in the agent's own response stream): "while that runs", "let me proactively work on later", "let me prepare US-XXX in parallel" (when the current story isn't `passed`).
3. **Self-recovery action**: log `[ORCH] STALE-DETECT: drifted; resetting to <current-story>` to stderr and re-read quantum.json's current `in_progress` story tasks.

The text lives in a new `### Self-monitoring guard` subsection between Step 4 and Step 4B (which handles full-feature review).

**Files:** `agents/orchestrator.md` (1 new subsection inserted; ~30 lines).

**Enforcement model — explicit:** This is a **prose-only advisory guard** consumed by the orchestrator LLM at agent-spawn time, NOT a runtime-enforced check. v0.6.7's failure was LLM-side context-drift; a prose patch cannot deterministically prevent it. The AC is therefore **presence-only**: the orchestrator HAS a documented self-monitoring guard (verifiable by grep) — not "the orchestrator WILL detect drift in all cases" (which would require LLM-side runtime instrumentation, out of scope for v0.6.8). A complementary parent-side liveness check (poll for committed changes after wall-clock; re-spawn or hand off) is queued as a separate v0.6.9+ candidate (see IDEA_REPORT_v9 § N6-followup).

**Verification:** new assertion in `tests/test_orchestrator_wiring.sh` (or a new dedicated test file): grep that orchestrator.md contains both `Self-monitoring guard` header AND the forbidden-idiom regex `while that runs|let me proactively`. ≥3 new assertions.

### US-002 — N7: soliton-finding-triage doc

**Problem:** v0.6.7's US-002 implemented a fix for soliton G36 (confidence 82) without first validating the bug existed empirically. The bug was a hallucination — the regex `|$` already handled the empty-input case. The fix shipped anyway as defense-in-depth (with regression-guard test as the durable protection) but the implementer-time wasted on the false-positive fix is a recurring risk for sub-threshold findings.

**Decision:** New committed reference `references/soliton-finding-triage.md` documenting the operator-side workflow:

1. For each sub-threshold soliton finding (score < 85) the operator chooses to address in the next cycle, write a 1-line empirical reproduction or counter-example BEFORE adding it to the design slate.
2. If the bug doesn't reproduce → file as a regression-guard test (lock in current correct behavior) instead of a fix story.
3. If it reproduces but is invasive → still possible to file as a fix story, but the design doc explicitly flags "verified by repro: <repro line>" so reviewers know the work is well-grounded.

**Files:** `references/soliton-finding-triage.md` (NEW, ~50 lines).

**Verification:** new test `tests/test_soliton_triage_doc.sh` (or extension to existing reference-doc audits): grep that the file exists, has 3 sections (Workflow / Repro template / Examples), and includes the v0.6.7 G36 case as a worked example.

### US-003 — N8: narrow Test 37a awk to function-header range

**Problem:** v0.6.6 G34's stated intent was "trim PR-metadata bloat from `quantum-loop.sh` function-header comments" — but Test 37a's `extract_function_comments` awk reads BOTH function-header AND function-body comments. The mismatch surfaced in v0.6.7 when c47e038's body comment in `do_audit` (added by a v0.6.6 post-merge soliton fix) tripped Test 37a — even though the function-header was clean. v0.6.7's US-001 fixed the body comment, but the test is still over-broad.

**Decision:** Narrow `extract_function_comments` to function-header range only:

```awk
extract_function_comments() {
  local fn="$1"
  awk -v fn="$fn" '
    /^'"$fn"'\(\) \{/ {
      # Function definition reached. Emit accumulated header buffer ONLY.
      for (i=1; i<=hbuf_n; i++) print hbuf[i]
      exit
    }
    /^[[:space:]]*#/ {
      hbuf_n++
      hbuf[hbuf_n] = $0
      next
    }
    /^[[:space:]]*$/ { hbuf_n=0 }
    { hbuf_n=0 }
  ' "$REPO_ROOT/quantum-loop.sh"
}
```

Removes the `in_body` state machine entirely. Tests 36b/37b's WHY-phrase assertion still works (function-header has the WHY); Tests 36a/37a's bloat-detection still works (header is what G34 trimmed). Body comments are now out of scope — matches G34's stated intent.

**Files:** `tests/test_audit.sh` (~20-line awk simplification + comment update noting N8/v0.6.8 scope clarification).

**Verification:** existing 45 audit assertions remain green; awk simplification preserves outputs. Confirm via:
1. `bash tests/test_audit.sh` → 45/45 PASS.
2. Inject a body-only "G99" comment into `do_audit` body → Test 37a now PASSes (was: would FAIL pre-N8).
3. Revert injection.

### US-004 — N9: wall-clock target calibration

**Problem:** v0.6.7's design + PRD specified `<60s` for `tests/test_audit.sh` wall-clock. Actual Git Bash wall-clock is ~3-4min due to per-process subprocess startup overhead (each `bash quantum-loop.sh --audit` subprocess in Tests 5/6/12/19/23/24/25/27/32/33 takes ~1-2s × ~30 invocations = ~60-90s of pure subprocess overhead). The 60s target was unmeetable on Git Bash.

**Decision:** New committed reference `references/test-wallclock-baselines.md` documenting platform-conditional baselines:

| Test command | Git Bash | Linux/CI | Macro-style note |
|---|---|---|---|
| `bash tests/test_audit.sh` | ~3-4min | ~30-60s | dominated by `bash quantum-loop.sh --audit` subprocess loops |
| `bash tests/run_all.sh` | ~17min | ~3-5min | sequential; 76 test files |
| `bash tests/run_all.sh --parallel 4` | ~5-8min | ~1-2min | xargs -P 4 dispatch |
| `bash tests/test_run_all.sh` | ~30s | ~5s | small fixture-driven |

Future test-time ACs reference these baselines: "completes within Git-Bash-baseline + 50%" or "within 2× of the platform baseline". No absolute-target language unless platform is specified.

**Files:** `references/test-wallclock-baselines.md` (NEW, ~30 lines).

**Verification:** existence test + reference link from `CLAUDE.md` Platform Notes.

**Baseline-drift detection deferred:** A meta-test that runs each baseline command with `time` and WARNS on >50% drift was suggested by v0.6.8 design-review but deferred to v0.6.9+ (queued in IDEA_REPORT_v9 § N9-followup). Adding it inline would scope-creep v0.6.8 and double the cycle's wall-clock during test runs. Hand-update is acceptable for now — operators refresh the baselines during retrospectives that observe drift.

### US-005 — N10: compute_risk_score doc-claim correction

**Problem:** v0.6.7's US-002 added a comment to `should_dispatch_deep_review` saying "Mirrors the structure used in compute_risk_score above." But `compute_risk_score` does NOT have an inner `if (( files_changed > 0 ))` guard — it relies on the outer `if [[ -n "$base_sha" && -n "$head_sha" ]]` (line 51) which short-circuits BEFORE `files_changed` is computed.

**Decision:** Rewrite the comment in `lib/deep-review.sh::should_dispatch_deep_review` to clarify the structural difference:

```bash
# G36 / US-002 (v0.6.7) — defense-in-depth guard. The `|$` alternative
# inside the regex below already excludes the empty trailing newline that
# `printf '%s\n' ""` produces on a 0-files diff (verified by Test 5 in
# tests/test_deep_review_dispatch.sh), so prod_count IS 0 on empty input
# today. The explicit `files_changed > 0` short-circuit hardens against
# any future refactor that removes the `|$` anchor.
#
# N10 / US-005 (v0.6.8) — note that `compute_risk_score` above does NOT
# have this inner guard; it relies on the outer `if [[ -n base && -n head ]]`
# at line 51, which short-circuits the whole block before files_changed
# is computed. The two functions handle the empty-input case via different
# mechanisms (outer SHA-presence check vs inner files_changed-count check),
# both correct.
```

**Files:** `lib/deep-review.sh` (1 comment block ~10 lines).

**Verification:** `bash tests/test_deep_review_dispatch.sh` → 14/14 PASS (no behavior change).

### US-006 — N11: move else-branch cleanup to LAST line

**Problem:** v0.6.7's US-004 (N1) restructured `agents/orchestrator.md` Step 4B.5 with explicit `if/else`. The else-branch's first action is `rm -f "$REPO_ROOT/.quantum-feature-diff.patch"` — but if steps 1-7 fail (jq error, missing dependency, etc.), the patch file is gone and operators can't inspect it for debugging.

**Decision:** Move the cleanup to AFTER step 7 (the verdict-case block) within the else-branch. Apply same pattern to the if-branch's existing cleanup so both branches have symmetric cleanup-at-end. Use the simpler "move to end" pattern (no `trap`).

**BLOCKS_MERGE edge handled explicitly:** when verdict=BLOCKS_MERGE the case statement does `exit 1`, so the cleanup line at the end of the else-branch is intentionally NOT reached. The patch file remains for forensic inspection by the operator triaging the blocked merge. Documented as the desired behavior — operator cleans up manually after BLOCKS_MERGE triage.

**Files:** `agents/orchestrator.md` (Step 4B.5 — move 2 `rm -f` lines).

**Verification:** Test 6 in `tests/test_deep_review_dispatch.sh` already verifies `else`/`fi` containment + `score-from-quantum` between them. New Test 7: assert `rm -f` appears AFTER `case "$VERDICT"` block in the else-branch (i.e., near closing `fi`).
